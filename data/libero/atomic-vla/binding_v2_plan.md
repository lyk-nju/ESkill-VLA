# 实例绑定规则优化方案

2026-11-01。状态：本方案已实现 v2，并完成固定 100 条回归与 26 条新增／变化轨迹的核验视频。结果：238 个 Event 中 236 个有唯一候选，原 192 个未改变；95 条区域完整且每帧事件唯一。人工待验收，v1 规则、标注和视频保留。下文保留本轮设计依据。

优化前固定 100 条中，74 条全部 Event 有规则候选，71 条完整产出。26 条绑定不完整里，22 条／36 个 Event 的信息已在任务与场景中，但规则未正确利用；另 2 条双摩卡壶需要实例消歧，2 条 Push／Pick 需要技能审核。3 条缺场景状态、014 的一帧事件重叠分别处理，不用绑定逻辑掩盖。

## 优先级与改法

| 顺序 | 修改点 | 对应当前问题 |
| --- | --- | --- |
| 1 | 分开解析动作、对象、部件、参照物，独立审核源技能 | Push／Pick 冲突不再导致 plate 对象信息一并丢失；源技能保留 |
| 2 | 按类别＋属性查询实体，按所属实体查询部件 | book、cabinet 的泛称；top drawer 被当作独立物体；白柜部件漏配 |
| 3 | 把完整短语查表改为关系解析＋场景查询 | on stove／cabinet、next to plate／ramekin、table center |
| 4 | 在同一任务和同臂事件中解析省略与身份延续 | close drawer 的 bottom 信息在任务中；Pick→Hold／Place 的对象连续性 |
| 5 | 为多候选及语义冲突接入实际接触和运动证据 | 两只摩卡壶；同时检查已有绑定是否与运动矛盾 |

前三项和任务上下文先做成纯数据逻辑，可独立检查 22 条覆盖缺口。运动证据随后接入；上述数字不是预计修复成功率。

## 1. 文本解析不直接选择实例

把“pick up the black bowl on the stove”解析为中间查询：

```json
{
  "action": "Pick",
  "object": {"category": "bowl", "attributes": {"color": "black"}},
  "part": null,
  "relation": {"kind": "on", "reference": {"category": "stove"}}
}
```

这是绑定器内部表示，不新增训练数据字段。类别泛称可匹配场景中的细分类，显式颜色、材质、位置仍作为约束；未知修饰语不能直接删掉。别名只归一化语义，不指向某个实例 ID。任务中的身份限定、Event 描述、Place 目的地分别保留；放到盘子上不等于当前操作对象是盘子。

解析结果与 `primary_action_verb` 分开核对。Push 描述可以得到 plate 候选，同时记录技能冲突；展示或输出 bbox 不代表该 Event 的技能标签已合格。源技能及文本不自动覆盖。

## 2. 从场景建立实体、部件、区域的归属

在 LIBERO 来源适配中读取：实体类别和属性、部件所属实体、区域所属实体、初始关系，以及可用的逐帧位姿／关节。

- `book` 查询“书”类别，场景只有一本时得到唯一候选；有多本时仍需属性或其他证据。
- `top drawer` 是部件描述。先查询具有该部件的柜体，再解析具体 body；两座柜体都满足时保留多候选。
- 木柜、白柜可共享“cabinet / drawer”的语义规则，具体 body／joint 名称由资产适配提供，并在编译模型中核验。

现有 `scene['regions'][region]['target']` 已提供区域归属。运行时 `object_sites_dict` 还提供 `parent_name`、`joints` 等信息，可复用，无需另建大型场景框架。部件语义并非一定能从任意 XML 名称自动推断，少量资产语义映射仍放在来源配置里。

## 3. 空间关系按查询执行

例如 `on stove`：先取得所有炉灶候选，再查其所属区域，最后筛选满足 `on(对象, 炉灶或其表面区域)` 的对象。该逻辑同样用于柜体、盘子或其他承托物，不按具体任务名分支。

`next_to`、`between`、`center` 是关系／区域语义。LIBERO 适配可以把已有命名区域转成这些语义，再由同一套查询匹配参照物；核心不保存 `next to plate → main_table_next_to_plate_region` 这样的完整句子映射。新场景缺少可解释的区域语义时，保留待补信息；名称拆解不能冒充任意模拟器都提供的结构化语义。

区分关系的时间：完整任务用初始位置指定对象时，记录为初始身份依据；Event 明确指向当前位置时，需要当前状态。搬动物体之后，不能把初始空间关系当成每帧仍成立。BDDL goal 和 obj_of_interest 不参与直接选择答案。

## 4. 上下文只补省略，不能覆盖冲突

明确的 Event 信息优先；省略部分从完整任务、同臂前序事件补充。多个相关描述必须同时兼容，不能因为 Event 更明确就忽略相互矛盾的任务约束。

`close the drawer` 可从该任务明确提到的 bottom drawer 补全部件；若任务涉及多个抽屉，结合相应前序操作和状态，仍有多种解释时保持歧义。不能仅凭“上一个提到的名词”或 Event 序号指定对象。

保留同臂 Pick→Hold／Place 的身份候选，在已有接触／持物证据支持时确认延续；释放、新 Pick、跨臂操作或显式不同对象会重新检查。源 Event 重叠与缺口单独报告，不自动改边界以满足继承条件。

## 5. 接触与运动按操作类型核验

| 操作 | 有意义的证据 |
| --- | --- |
| Pick | 持续夹爪接触、对象与夹爪运动关联、抓取后相对位姿稳定 |
| Hold／Place | 已确认对象身份、持物关系的持续／释放；静止 Hold 不要求对象移动 |
| Open／Close／Turn | 所选部件的关节变化和局部接触；柜体根节点不移动也可能在操作 |
| Push | 接触期间物体位移与推送关联，不要求抓持；技能冲突另行保留 |

距离和位移用于支持证据，不默认选择最近或移动最多的对象。证据不足或多候选同样合理时保留歧义。参数按操作语义设定，并用反例核验后固定，不为每条轨迹单调阈值；当前展示 10 fps 也不能直接当作源采集频率。

接触继续读取 MuJoCo 实际碰撞对和正确部件的碰撞几何。已核对本地 `SiteObjectState.check_contact()` 对区域会直接返回 True；不能把它作为真实物理接触。区域 in/on 判断也含几何近似，只作为相应证据。恢复状态有来源残差时记录质量，不用随机场景或未匹配回放填补。

## 代码与输出保持简洁

新版本绑定器按四组函数组织：文本解析、场景查询、上下文解析、证据核验；来源目录内保存小规模类别／资产配置。继续复用 `source.py` 的原始字段读取、`resolve_geometry` 的几何解析及共用渲染器，不新增插件框架。

输出保留现有 `instance`、`scope`、`status`、`evidence` 等核心字段，另记录技能一致性；绑定成功、几何可解析、物理证据支持、人工通过分别计数。`motion` 未运行应记 not_measured，不能再用 no_matched_states 代替。

v1 代码和报告作为固定基线保留；新版本用独立入口和 `check/test/binding_v2/` 输出，视频仍放 `check/test/video/`。在验证接口后接入批渲染，不能让新旧结果共用缓存或悄悄覆盖已核验视频。

## 验证与进入下一阶段的条件

1. **机制检查**：实例重命名、候选顺序打乱、加入同类干扰物；换对象类别复用 on/in；多个柜体、未知属性、矛盾描述、跨臂和释放；Push／Pick 独立记录；部件动而柜体不动；两物体都动但只有一只被持续抓持。
2. **固定 100 条回归**：输出逐 Event 的旧／新候选及理由。既有 192 个候选有变化时逐项核对；新增绑定单独检查，不只报覆盖率上涨。014 重叠与三条缺场景保持可见。
3. **人工验收**：重点渲染新增绑定和发生变化的轨迹，核对当前对象、完整屏内框及同对象 Event 终点。
4. **泛化验证**：另外选未用于制定规则的任务／对象关系组合，先固定样本再运行。这 100 条都参与过分析，不能重新随机划分后声称是未见评估。
